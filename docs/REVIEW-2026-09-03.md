## 一句话结论

架构选型正确、接缝用法与宿主契约一致、测试基础扎实；但 v0.5.0 引入的「普通子代理首请求前路由」修复带来了一个**静默降档的回归**（`tier_worker` 显式强档会被策略路由改成弱档），回退链漏掉了适配器真实会发出的两个错误码，回退与宿主自带重试的先后顺序依赖监听器注册次序。这三处已在 0.5.1 修复并配回归测试；其余为设计层与工程层建议，进入 `docs/ROADMAP.md`。

## 做得好的地方（值得保持）

- **纯逻辑/副作用分层**：`lib/pure.js` 无 I/O、无宿主依赖，守卫矩阵、档位决策优先级、回退状态机、配置迁移都可以离线测。这是这个项目最值钱的工程决定。
- **守卫锚定命令位置**：`hasRecursiveForceRm` 区分「带参数的 runner」与「直接 runner」，散文不误伤，这比常见的 `includes('rm -rf')` 高一个档次。
- **注册隔离**：`safeRegister` 让某个工具/命令名冲突不会拖死整个插件。
- **preset 同步的所有权模型**：带 marker 的目录才覆盖，无 marker 的分歧目录先备份，不会吞掉用户改过的 preset。
- **mock 宿主 smoke 套件**：`tests/smoke.test.mjs` 以真实 `apply()` 加 mock 服务跑通每条工具/命令/监听器路径，是本轮能在不起 DSH 的情况下做负控制验证的前提。
- **双语文档 + CHANGELOG + 打包回归**：对一个个人插件来说已经超过平均水平。

## 发现清单（按严重度）

### 1. [高] `tier_worker` 显式档位被子代理策略路由覆盖 —— 已修（0.5.1）

- **现象**：`mode=auto`、计划未激活、`subagentPolicy=inherit` 时调用 `tier_worker({ tier: 'strong' })`，子代理实际跑在弱档；反过来 `subagentPolicy=strong` 时 `tier: 'cheap'` 的 worker 跑强档（成本翻倍）。工具返回值里的 `tier/provider/model` 仍显示请求的档位，所以是**静默**错误。
- **根因**（源码核对）：`dsh-subagent-in-process-driver` 在 `start()` 内部先 `agents.create({ agentOptions })`，再在 `drivePublishedRun` 里同步 `child.followup(prompt, source:{kind:'user'})`，然后才把 run 返回。插件在 `settleRun` 拿到 `run.localAgent` 之后才 `childTiers.set(...)`，而此时子代理的 `agent/inbox/inserted` 已经触发过，处理器里 `resolveTarget(child)` 看不到 explicitTier，按 policy/plan 决策并 `applyTarget` 覆盖了 `agent.options` 与 header。这是 v0.5.0「普通子代理首请求前应用策略」修复的副作用。
- **修复**：工具在 `subagents.start()` 之前把请求的路由登记到 `pendingWorkers`（60s TTL），inbox 处理器对未登记 `childTiers` 的子代理先 `adoptPendingWorker()`（按 provider/model 匹配），再做路由；`settleRun`/start 失败都会清理登记。
- **验证**（单元验证）：新增 `tier_worker child keeps its explicit route and effort when the inbox listener runs first`，并做了负控制：注释掉 `adoptPendingWorker(agent)` 该测试失败，恢复后 86/86 通过。同时新增对照测试确认未登记的普通子代理仍按策略路由到弱档。
- **附带收益**：修复后子代理首请求前 header 已带上档位 effort，弥补了 `AgentOptions` 不含 `reasoningEffort` 的宿主限制。
- **修复的前提与残余风险**（M1 实机验收要覆盖）：
  - 领养门槛依赖 `agent.session.header.origin === 'subagent'`。源码核对：`childSessionMeta()` 返回 `origin: "subagent"`，`dsh-session` 创建会话时把 `meta.origin` 写进 header（L1665），所以门槛成立。
  - 依赖 `agent.options` 可变（0.5.0 已经依赖这一点），只有单元验证。
  - 领养按 provider/model 匹配，不看父代理。若 `start()` 等待期间恰有一个普通 `subagent` 子代理继承的 options 与登记路由相同，它可能先领走这条登记：`inherit` 策略下无害，`strong/cheap` 策略下会让那个普通子代理跳过策略路由。改成同时匹配父代理身份即可根治，列入 M8。
  - `followSession` 开启时，领养后的强档 worker 会被 `effectiveTarget` 改到会话选择的模型，而工具返回值仍报 `state.strong` 的 provider/model（发现 7 的根因），此时「报告的模型」与「实际模型」可能不一致。

### 2. [中] 回退链漏掉适配器真实发出的 `TIMEOUT` 与 `NO_ADAPTER` —— 已修

- **证据**（源码核对）：`dsh-llm-deepseek` 发 `TIMEOUT/SERVER/RATE_LIMIT/TRANSPORT/MISSING_CREDENTIAL`；`dsh-llm-pi-ai` 另发 `UNKNOWN_MODEL/NO_ADAPTER`；llm core 发 `QUOTA/NO_ADAPTER/INVALID_CREDENTIAL/UNKNOWN`。`TIMEOUT`（provider 挂起）和 `NO_ADAPTER`（路由没有适配器）之前会走 `escalate` 分支，即只计入失败升级、不切回退链。
- **修复**：两码加入 `FALLBACK_TRIGGER_CODES`，注释写明来源版本。`UNKNOWN` 仍保留为 `escalate`（语义不明）。

### 3. [中] 回退与宿主 `dsh-llm-retry` 的先后依赖监听器注册次序 —— 已修

- **证据**（源码核对）：`dsh-llm-retry` 也监听 `agent/request-error`，对 `retryableCodes` 内的失败自行退避（尊重 `providerRetryAfterMs`）并直接返回 `retry`，直到 `maxRetries` 耗尽才 `next()`。插件原来对可回退码**不调用 `next()`** 直接切路由：若插件先于 llm-retry 执行，就跳过了宿主退避，一次 429 就换模型。
- **修复**：先 `await next()`，下游返回 `retry` 就原样返回，下游放弃（`undefined`）才推进回退链；`signal.aborted` 时不再动路由。这样与注册顺序无关。真实进程里当前的顺序**未实机核对**，修复后也不再需要知道。

### 4. [中] 守卫可被 shell 包装绕过 —— 最小修复，其余留决策

- 已修：`sh -c "rm -rf x"`、`bash -lc '…'`、`zsh -c …`、`eval "rm -rf x"` 现在会被拦；`sh -c "echo rm -rf"`、`sh script.sh` 不误伤（有测试）。
- **未改、留 ROADMAP 决策**（都会增加弱档拒绝频率，需要用户拍板）：`git reset --hard`、`git branch -D`、`git checkout -- . / git restore .`、`rsync --delete`、`node -e … rmSync` / `perl -e unlink`、`truncate -s 0`、`docker system prune -a`、`kubectl delete`、`terraform destroy`、`DROP TABLE/DATABASE`、`npm publish`、Windows 的 `pwsh` 工具（`Remove-Item -Recurse -Force`）完全没有守卫。
- **定位要写清**：守卫是确定性的**减速带**，不是权限边界（见发现 6）。文档应明说它拦的是「弱档不该直接做的高危动作」，而不是「所有危险动作」。

### 5. [中·设计] 思考强度阶梯的触发信号语义错位 —— 未改，建议

- 现在三种触发：弱档重试错误、守卫拒绝、显式工具。前两种都不是「任务太难」的证据：`QUOTA/RATE_LIMIT/TIMEOUT` 是可用性问题，守卫拒绝是权限问题；把 effort 从 medium 抬到 high/max 只会更慢更贵，不解决触发它的原因。
- 建议：保留显式工具与 `/tier effort`；错误触发改成「同一 turn 内工具结果连续 error ≥ N」（`tools/post-execute` 或 `tool/result` 事件可得），那才是模型在这个任务上吃力的信号。见 ROADMAP M5。

### 6. [中·安全模型] 弱档模型可自行升级、可持久化改全局配置 —— 未改，建议

- `tier_route strong` 是模型可调用工具，守卫的拒绝理由又直接教模型去调它：弱档想做高危动作只需多一步。这在「升级=用更强模型」的设计里是可接受的（目的是换脑子不是拦人），但要在文档里说清。
- `tier_configure` 默认 `sessionOnly: false`，模型一次调用就能把弱档改成更贵的模型、清空回退链、改子代理策略，并持久化到 settings。建议：默认改为 `sessionOnly: true`，持久化需显式 `persist`/`durable: true`；或在 `tools/pre-execute` 对 `tier_configure` 返回 `ask` 走宿主审批。见 ROADMAP M2。

### 7. [低] `tier_worker` 不走 `strongStandaloneTarget()`

- advisor/review 在 `followSession` 时跟随会话选择，`tier_worker` 直接读 `state.strong`，两处对「强档是什么」的答案不同。行为变更，留 M8。

### 8. [低] 默认强档回退链等于主路由本身

- `DEFAULT_TIER_CONFIG.strong.fallback` 是同一 provider/model/effort，等于「失败后再试同一个」，只是多一次尝试。要么置空、要么换到另一条路由（如 `opencode-go`）。留 M8，因为它改变默认行为。

### 9. [低] 可观测性：diag 计数器是进程全局，路由变更没有审计事件

- `/tier status` 的 `requestSteps/guardChecks/...` 在多会话进程里混在一起；每次 `applyTarget` 只更新 `diag.lastHeader` 字符串。没有「这个会话在各档各花了多少 token」的数据，也就无法回答这个插件最该回答的问题：**省了多少钱**。见 M6。

### 10. [低] 会话级模式只存内存

- `sessionModes` 是 WeakMap，DSH 重启后所有恢复的会话回到全局默认；`/tier off` 的会话会被重新管理。已在 README「已知限制」补上；持久化方案见 M3。

### 11. [低] 结构：`apply()` 一个闭包 1300 行

- 状态、回退、守卫、7 个工具、2 个命令、提示词段落全在一个函数里，靠闭包共享 20 多个变量。现在还能读，再加两个功能就不行了。见 M7。

### 12. [低] 兼容矩阵

- npm 上 `@deepseek-ai/dsh-agent` 的 `latest` 是 rc.6、`next` 是 0.1.2-rc.1，本机跑的是 rc.8，CI 只针对 rc.8。事件契约三者一致（见上表），但 0.1.2 的其它包（subagent 驱动、llm-retry）未核对。建议 CI 加一个允许失败的 `@next` job。见 M8。

### 13. 文档问题 —— 已修

- README 中英文开头第一句都从半句开始（英文缺主语句，中文缺「`/advisor` 与 `opusplan`」那半句）。
- 「npm test — 20 cases」实际 80（现在 86）。
- CHANGELOG 0.5.0「Changed: cheap = cctq/gpt-5.6-terra…」与代码默认值（`deepseek-v4-flash@medium`、无回退）矛盾，那是本地测试配置。
- README 缺「会话模式不持久化」限制。
